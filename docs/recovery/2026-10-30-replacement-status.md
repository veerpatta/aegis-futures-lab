# Reconstructed owner controls: review and deployment notes

This is new implementation, not the lost original code. The migration pins the sole existing unbanned administrator as owner, and refuses to run if that precondition is false. Private journal and CRM RLS checks that pinned identity, current administrator role and ban status. The web API verifies the Neon JWT and rechecks that role in the database. The trusted worker rechecks and locks the account before acting. Public pages remain readable. Neon Auth provider-level signup endpoints are unchanged.

The prepared SQL is `2026-10-30-prepared-connector.sql`. The Neon preparation ID is `1375e1a4-fe4f-4bdb-84bd-4f037dd868ba`, project `floral-cell-79900814`, database `neondb`, parent `br-small-mode-b3y8iq6w`, test branch `br-blue-breeze-b3td5y4e`. Preparation is not a production application. The earlier test preparation `e4cac988-8a72-487e-badb-88637e1cba45` on `br-summer-forest-b3q9lc2n` is superseded and must not be applied. Connector completion or discard explicitly requires user confirmation; retain the exact SQL for either operation.

New production permissions proposed: `authenticated` may execute `public.aegis_is_owner()` (a boolean-only security-definer check); `aegis_ai` may select `public.admin_control_authorized` and select the command queue and insert only its id, owner, action, reason and expected campaign columns. The existing `aegis_ai_app` credential inherits `aegis_ai` and would therefore be able to read all command reasons/results and enqueue a command attributed to Raj while he remains an unbanned administrator. The browser roles cannot read or write that queue. The service cannot update or delete commands. These grants are needed for the existing restricted server connection to verify the current owner and enqueue or list commands; the privileged worker completes them. They do not add login credentials or role memberships. They are a permissions expansion and are not authorized for production by the earlier no-expansion constraint without specific action-time confirmation.

The worker processes commands on a genuine tick trigger. It rechecks current administrator status, shares locks with tick and learning, refuses stale campaigns, and records a result atomically. The owner's original reason stays in the private queue; public status and history contain a fixed generic reason and command reference. Pause keeps managing virtual positions. Stop refuses while a virtual position or pending fill remains; a new campaign also requires no remaining positions and preserves the prior ledger. Commands may remain pending over the weekend or if the scheduler is unavailable. This work does not initiate real trades or paid AI calls.

On the v2 isolated branch, role revocation made the owner predicate and admin view false; rollback restored the role. Using the existing `aegis_ai_app` login, an owner command could be inserted and a forged owner was rejected by RLS. Using the existing `authenticator` login and `authenticated` role, synthetic journal and CRM records were visible to the owner and invisible to another subject; both transactions rolled back. Privilege inspection showed browser roles lack queue SELECT, the service lacks UPDATE and cannot insert the status column, and can insert the reason column. Duplicate pending commands and rewriting a completed command were rejected, and the failed command test transactions left no rows. Direct `SET ROLE aegis_ai` as `neondb_owner` was denied, but the existing service login supplied the role-level test.

A separate local PostgreSQL 17 container with synthetic data ran the actual `PgStore` worker and `tick` concurrently. The worker waited on the held tick lock, then atomically applied pause and its audit. A forced database error rolled back the state change and audit while recording a failed command; revoking the synthetic admin caused rejection without changing the learner. This validates the tested local database path, not production infrastructure or every concurrency interleaving. Four additional regression cases check that pause, resume, stop and start never copy private free-text reasons to public learner writes.

Deployment must be sequenced only after full review, checks and approval of the specific grants: verify the exact production branch, account and backup/recovery point; deploy the tested Neon learner function first (it does nothing with commands until the table exists), then the reviewed Vercel application, then apply the exact prepared migration using its preparation context. Between application deployment and migration, owner controls and private AI routes fail closed; public pages remain available. This order avoids an interval after migration when the old AI routes still accept any signed-in user. Verify deployment identities and read-only paths. Do not submit a control command or change a password just to test live.

If deployment fails, stop and inspect state before retrying. Rolling the application back to the old commit restores its broader signed-in AI access and does not undo database policies or recorded commands. The old worker would leave queued commands pending. A recovery plan must preserve private restrictions and command records; do not automatically drop the audit queue, remove privacy policies or blindly restore the old application.
